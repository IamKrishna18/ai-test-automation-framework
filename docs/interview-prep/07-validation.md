# Validation Strategy (Phase 10)

Because AI outputs can be unreliable, the framework enforces a two-tier validation system before any test is executed against a target API.

## 1. Schema Validation
Implemented in `schema_validator.py`.
- **Goal**: Ensure the generated test case is structurally sound and type-safe.
- **Mechanism**: The dictionary parsed from the LLM response is loaded into a Pydantic model (`GeneratedTestCase`).
- **Failure Cases**: Missing required fields, incorrect data types (e.g., string instead of an integer for status codes), or malformed JSON strings in parameters/headers. Any `ValidationError` is caught, and exact localization (`loc`) and messages are recorded.

## 2. Semantic Validation (Anti-Hallucination)
Implemented in `semantic_validator.py`.
- **Goal**: Ensure the test case makes logical sense within the context of the specific API being tested.
- **Mechanism**: The generated `TestCase` endpoint and HTTP method are cross-referenced with the `ParsedSpec` derived from the user's OpenAPI document.
- **Path Parameter Resolution**: The validator intelligently standardizes paths by converting OpenAPI path templates (e.g., `/users/{id}`) into regular expressions (`^/users/[^/]+$`) so it can match concrete endpoints generated by the AI (e.g., `/users/123`).
- **Failure Cases**: If the AI attempts to `POST` to a read-only `GET` endpoint, or invents a path like `/admin/delete_all` that does not exist in the spec, semantic validation fails, and the test is marked "invalid".
