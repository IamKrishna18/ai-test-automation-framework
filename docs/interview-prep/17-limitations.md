# 17. Limitations (Phase 22)

Be upfront about the boundaries of the framework. Interviewers appreciate engineers who know what their software *cannot* do just as much as what it *can* do.

## 1. Complex Authentication State

**Limitation:** The framework currently handles simple static headers (e.g., passing an API key or a static Bearer token).
**Why it's a problem:** It cannot handle complex, multi-step authentication flows (OAuth 2.0 Authorization Code flow, session cookies requiring a prior login request, token refresh logic).
**Potential Fix:** Introduce a "Setup/Teardown" phase where the system can execute predefined authentication scripts or inject dynamic variables from a prior request into the test's headers.

## 2. API State Dependencies (Test Isolation)

**Limitation:** Tests generated by the LLM are evaluated largely in isolation.
**Why it's a problem:** The AI might generate a `DELETE /users/123` test. If executed first, it might pass. If a subsequent test tries `GET /users/123`, it will fail. The framework does not guarantee execution order or state isolation (like resetting the DB before each test).
**Potential Fix:** Implement dependency graphs for tests (e.g., POST must run before GET, which runs before DELETE). Or, better yet, recommend the target API be run in an ephemeral Docker container that resets per test suite run.

## 3. Large OpenAPI Specifications

**Limitation:** The context window of the LLM.
**Why it's a problem:** If a user uploads an OpenAPI specification with 500 endpoints, sending the entire document in the prompt will exceed the token limit of most models, or severely degrade the model's reasoning capabilities (the "Lost in the Middle" phenomenon).
**Potential Fix:** Implement a Retrieval-Augmented Generation (RAG) approach or chunking strategy. Parse the spec, and iteratively prompt the LLM to generate tests for one endpoint (or a small batch of endpoints) at a time.

## 4. Non-RESTful APIs

**Limitation:** The current semantic validator and HTTP executor assume a strict REST HTTP paradigm (GET, POST, PUT, DELETE with JSON payloads).
**Why it's a problem:** It cannot test GraphQL endpoints (which usually sit on a single `/graphql` POST route and require specific query structures), gRPC, or WebSockets.
**Potential Fix:** The execution engine would need to be abstracted into interfaces (e.g., `RestExecutor`, `GraphQLAdapter`, `WebSocketListener`) and the LLM prompt adjusted heavily to support these protocols.

## 5. Security Vulnerability Testing

**Limitation:** The framework is designed for functional and edge-case testing, not comprehensive penetration testing.
**Why it's a problem:** While the AI might try basic SQL injection strings if prompted, it is not a replacement for dedicated security scanners (like OWASP ZAP or Burp Suite). The LLM might generate malicious payloads that actually damage the target system if it's not properly sandboxed.
**Potential Fix:** Restrict the AI's prompt to explicitly forbid destructive payloads unless a specific "Security Mode" toggle is enabled, and rely on specialized tools for actual security audits.
