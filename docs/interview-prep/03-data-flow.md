# Data Flow: Test Generation & Execution Cycle

This document traces the complete life of a test run from the user's initial request to the final generated results.

## 1. Test Run Initialization
1. **User Action**: The user fills out the "New Run" form in the React frontend (`RunCreator.tsx`), providing an OpenAPI spec, target URL, and selecting an AI provider/model.
2. **API Request**: The frontend makes a `POST /api/runs` request with the configuration payload.
3. **Database Insertion**: The FastAPI controller (`app.api.runs.create_run`) uses `RunRepository` to insert a new `TestRun` record with status `pending` into the SQLite database.

## 2. AI Test Generation
1. **User Action**: User triggers generation. Frontend calls `POST /api/runs/{run_id}/generate`.
2. **Orchestration**: The request hits `OrchestratorService.generate_tests`.
3. **Prompting**: `RunService` pulls the saved OpenAPI spec, injects it into a structured LLM prompt, and requests a specific JSON schema using `BaseLLMProvider`.
4. **Parsing**: The LLM provider (e.g., Gemini) returns a structured JSON payload of test cases. `RunService` maps these into `TestCase` database entities.

## 3. Strict Validation Pipeline
Before executing anything against a real server, the framework ensures AI correctness:
1. **Schema Validation**: `SchemaValidator` verifies that required fields (method, endpoint, expected_status) exist and are properly typed.
2. **Semantic Validation**: `SemanticValidator` cross-references the test against the `parsed_spec`. It checks:
   - Does this endpoint actually exist in the OpenAPI spec?
   - Is the HTTP method allowed?
   - Are required parameters included?
3. **Status Update**: Tests passing both checks are marked `valid`. Failed ones are marked `invalid` with attached error messages.

## 4. Execution & Evaluation
1. **Triggering Execution**: Frontend calls `POST /api/runs/{run_id}/execute`.
2. **Executing**: `OrchestratorService.execute_run` initializes `HttpExecutor`. It iterates *only* through `valid` test cases.
3. **Network Call**: The executor crafts an async HTTP request to the target API based on the AI-generated endpoint, method, headers, and body.
4. **Result Evaluation**: The HTTP response is handed to `ResultEvaluator`. It compares the actual status code and payload structure against the `expected_status` and `expected_fields` generated by the AI.
5. **Persistence**: The evaluated result (pass/fail/error) is saved via `TestResultRepository`, and the aggregate run stats (passed/failed counts) are updated.

## 5. Reporting
1. **Frontend Fetch**: The `RunDetails.tsx` view polls or requests `GET /api/runs/{run_id}` and `GET /api/runs/{run_id}/results`.
2. **Display**: The UI visualizes the pass rate, shows detailed JSON request/response logs, and highlights why any specific test failed or was flagged as invalid by the validator.
